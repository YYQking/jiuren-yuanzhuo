# 九人圆桌混合讨论模式设计

## 1. 目标与边界

本设计把“九人圆桌”从按顺序播放的观点列表升级为可持续的混合型讨论：九个角色先分别提出观点，再围绕共识、冲突和未回答问题自由交锋；角色可以多次发言、点名回应并改变立场；主持人根据讨论状态介入整理；用户可以随时插话、暂停、继续或结束。

讨论不设总轮数上限。系统只限制单次调度批次的发言数量，以避免界面冻结；该批次限制不影响用户继续讨论。

本阶段只定义讨论协议、事件流、状态跟踪和现有桌面 UI 的行为。默认仍为离线模式，离线模拟内容、真实模型内容和外部素材必须保持来源区分，不能把推断显示为已验证事实。

## 2. 讨论协议

### 2.1 阶段

讨论按以下状态循环：

1. **开题**：主持人重述主题、限制条件和本阶段问题。
2. **首轮观点**：参与的角色各自提出初始立场和依据。
3. **动态交锋**：角色根据前文支持、反驳、追问或补充；同一角色可连续多次发言。
4. **状态整理**：只有在状态触发时，主持人才整理共识、分歧、未回答问题和下一步重点。
5. **继续交锋**：围绕尚未解决的重点进入下一批发言，直到用户结束。

“状态整理”不是固定轮数或固定时间触发。状态监测器在新观点明显减少、重复增加、讨论冷场、重要共识出现或某个分歧已经充分交锋时触发主持人介入。

### 2.2 回应机制

采用混合点名：角色优先自行选择回应对象，可以在一条发言中支持、反驳或追问一个或多个角色；当关键分歧无人回应、讨论冷场或话题偏离时，主持人指定最相关的角色接话。

每条角色发言应尽量表达以下意图之一：`support`、`challenge`、`question`、`elaborate` 或 `synthesize`。回应对象、意图和对应的前文事件作为结构化元数据保存，而不是只从文本中猜测。

### 2.3 立场变化

角色允许改变观点。改变时必须记录：

- 变化前的立场；
- 变化后的立场；
- 影响变化的发言或理由；
- 仍然保留的条件、疑虑或限制。

角色也可以明确表示“部分接受”“暂不改变”或“强化原立场”，避免把礼貌性附和当成立场转变。

### 2.4 用户控制

- **插话**：用户内容作为高优先级上下文事件保存，下一批发言必须优先回应；不改写已经发生的发言。
- **暂停/继续**：暂停展示和调度，保持全部事件与状态；继续后从未完成的调度点恢复。
- **结束并总结**：停止待生成任务，只使用已经保存的事件生成总结；不等待未返回的角色发言。

## 3. 事件流与状态模型

### 3.1 事件流

每次讨论保存为有序、追加式事件流。事件至少包含：

| 字段 | 说明 |
| --- | --- |
| `event_id`、`sequence`、`created_at` | 稳定标识、顺序和时间 |
| `type` | `host_prompt`、`utterance`、`user_interjection`、`phase_summary`、`system_notice` 等 |
| `speaker_id` | 主持人、九个角色、用户或系统 |
| `phase` | 当前讨论阶段 |
| `addressed_to` | 被回应的角色或问题，可为空 |
| `intent` | 支持、反驳、追问、补充或整理 |
| `content` | 完整可读文本 |
| `source` | `user`、`offline_simulation`、`model` 或 `system` |
| `verification` | `not_applicable`、`unverified`、`pending` 等 |
| `stance_change` | 可选的变化前、变化后、理由和引用事件 |

重复内容不删除，只增加重复标记和检测依据，确保记录可追溯。

### 3.2 状态快照

事件流旁维护可重建的状态快照：

- 当前共识及其引用事件；
- 当前冲突及双方立场；
- 未回答问题及优先级；
- 重复观点计数和新观点密度；
- 每个角色的当前立场、信心和变化轨迹；
- 当前活跃分歧线程；
- 上次主持人介入原因；
- 当前阶段、运行状态和待处理用户插话。

快照是加速恢复和 UI 展示的派生数据，事件流是事实来源。历史加载时应优先加载已保存内容，不联网、不重新生成。

## 4. 调度与数据流

1. 创建会话，保存主题、选中的角色和生成来源。
2. 写入主持人开题事件。
3. 逐个生成首轮角色观点，并在每条事件落盘后更新快照。
4. 状态分析器提取共识、冲突、未回答问题和重复度。
5. 调度器为每个角色建立候选回应，优先级依次考虑：回应用户插话、解决未回答问题、澄清高冲突分歧、带来新信息、补充已有观点。
6. 生成一批有限数量的发言。批次内部允许角色重复发言和互相点名，但不能造成界面阻塞。
7. 状态监测器判断是否触发主持人整理；若触发，写入带介入原因的 `phase_summary`，然后继续下一批交锋。
8. 用户插话时立即落盘并提升调度优先级；下一批必须有针对性回应，无法回应时显示待处理状态。
9. 用户结束后取消或忽略未返回任务，基于完整事件流生成机会档案和讨论总结。

## 5. 圆桌 UI 行为

- 顶部 HUD 显示主题、当前阶段、运行状态、已保存发言数和生成来源；不扩展成后台工具栏。
- 当前席位、头像、姓名、气泡和底部字幕同步高亮；完整文本继续进入右侧记录抽屉。
- 每条记录显示角色、阶段、回应对象、发言意图和来源标签；立场变化显示“改变立场”标记并可展开理由。
- 主持人整理使用独立视觉样式，并显示介入原因，例如“重复增加，整理当前分歧”。
- 右侧状态区持续显示共识、分歧和未回答问题，并突出当前活跃分歧。
- 底部固定提供插话、暂停/继续、结束并总结；插话提交后显示用户回显。
- 总结页增加立场轨迹、未解决分歧、未验证假设和引用的关键发言。
- 离线模拟和真实模型内容始终显示来源；真实模型观点标记为未核验。

## 6. 异常与恢复

- 单个角色生成失败：记录“角色暂时无法发言”的系统事件，其他角色继续，不伪造该角色内容。
- 模型超时或网络错误：自动重试一次；仍失败则暂停当前生成，允许继续离线讨论或稍后重试。
- 状态分析不确定：标记为“待确认”，不能直接计入共识。
- 结束时：立即停止待生成任务，仅纳入已经返回并保存的事件。
- 每条事件生成后立即保存；重启可恢复最近状态。
- 缺失头像或资源使用安全占位，不阻塞讨论。
- 历史文件损坏时显示可理解的错误并保留其他历史，不使应用崩溃。
- 错误、取消、回退和静默音频都必须如实展示，不包装成成功；任何 API Key、请求头或敏感异常都不写入事件、历史或导出。

## 7. 总结与导出

结束总结必须包含：机会方向、目标用户、支持理由、风险、未验证假设、下一步行动、共识、分歧、未回答问题、角色观点分布和立场变化轨迹。

JSON 与 Markdown 导出包含主题、角色、时间、完整事件流、用户插话、机会档案、来源、provider、网络/生成状态、回退说明和适当的 usage 信息；不只导出当前字幕，也不导出秘密信息。

## 8. 验收标准

1. 九个角色可在同一阶段多次发言，并明确回应、支持、反驳或追问其他角色。
2. 系统能根据新观点减少、重复增加、冷场、重要共识或分歧充分交锋，自动插入主持人整理。
3. 角色改变观点时可查看变化前、变化后和触发理由。
4. 用户插话后，下一批发言优先回应插话。
5. 暂停、继续和结束都不会丢失已保存事件。
6. 总结页展示共识、分歧、未回答问题、立场变化、未验证假设和行动建议。
7. 失败角色、模型错误和低置信度分析有明确状态，不能伪装成正常结论。
8. 历史记录重新打开后，讨论流、状态和总结与保存内容一致。

## 9. 明确不包含的内容

本设计不引入固定轮数上限、自动联网 RSS、未经许可的真实模型调用、来源事实核验、角色语音、复杂粒子特效或新的安装器流程。这些内容需要单独确认和设计。
